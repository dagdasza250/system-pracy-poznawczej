## 2. U01 — Relation.from / Relation.to

### Problem
Schema definiuje `Relation` jako `id + from + type + to`, ale `from` i `to` są tylko identyfikatorami bez typu docelowego. Seed wykorzystuje dziewięć relacji i wszystkie endpointy są ID obiektów `Unit`.

### Decyzja
`Relation.from` i `Relation.to` są w **minimalnej ontologii eksperymentalnej v0.5.1 ograniczone do Unit**.

```text
ENDPOINT DOMAIN = Unit
POLYMORPHIC = NO
CLASSIFICATION = SEMANTIC_EDGE / UNIT_ONLY
```

### Uzasadnienie
To jest najmniejsza semantyka bezpośrednio wsparta istniejącym użyciem baseline'u. Nie ma dowodu, że v0.5.1 wykorzystuje `Relation` do łączenia Hypothesis, Model, Action lub innych typów. Otwarcie endpointów polimorficznych byłoby rozszerzeniem ontologii, a nie doprecyzowaniem istniejącego instrumentu.

### Granica
R2.2-A nie ustala jeszcze, czy oba endpointy muszą należeć do tej samej Case, czy self-loop lub duplikaty są dozwolone, które typy relacji są symetryczne ani minimalnej/maksymalnej liczby relacji. To należy do R2.2-B.

**U01 = RESOLVED**

## 3. U02 — Fragment.contextBeforeIds / contextAfterIds

### Problem
Schema definiuje oba pola jako `string[]`, ale nie podaje typu obiektu docelowego. Seed pozostawia je puste, a aplikacja przy tworzeniu Fragment również zapisuje puste listy.

### Decyzja
Nie przypisujemy im wymyślonego typu docelowego.

```text
TARGET TYPE = UNRESOLVED
CLASSIFICATION = UNRESOLVED_SCHEMA_GAP
CANONICAL CORE RELATION = NO, pending later resolution
OWNER SEMANTICS = R2.5 Provenance
OWNER CONFORMANCE = R2.7 Schema Conformance
IN R2.2-B CARDINALITY MATRIX = EXCLUDED
```

### Uzasadnienie
R2.2 ma formalizować to, co baseline rzeczywiście wspiera. Nazwa pola sugeruje kontekst, ale sama nazwa nie jest wystarczającym dowodem typu referencji. Bloker zostaje zamknięty przez jawne odroczenie, a nie przez zgadywanie.

**U02 = RESOLVED_AS_DEFERRED_SCHEMA_GAP**

## 4. U03 — Action.caseId

### Problem
Seed i `actionModal()` zapisują `caseId` wewnątrz Action, ale `$defs/action` w JSON Schema nie definiuje tego pola. Jednocześnie Action jest już przechowywany wewnątrz `case.actions[]`.

### Decyzja

```text
Action.caseId
CLASSIFICATION = IMPLEMENTATION_REFERENCE
ROLE = REDUNDANT_BACKLINK
CANONICAL ONTOLOGY RELATION = NO
CANONICAL CASE MEMBERSHIP = containment in Case.actions[]
IN R2.2-B CARDINALITY MATRIX = EXCLUDED
R2.7 = record schema/data/app divergence
```

### Uzasadnienie
`caseId` nie wnosi nowej semantyki potrzebnej do ustalenia przynależności Action do Case, ponieważ przynależność jest już strukturalnie wyrażona przez `Case.actions[]`. Uznanie obu za równorzędne źródła prawdy stworzyłoby potencjalną niespójność.

**U03 = RESOLVED**

## 6. Dodatkowe ustalenie: Result ↔ ModelVersion

Baseline nie posiada bezpośredniej referencji ID pomiędzy Result i ModelVersion-record. Aplikacja po utworzeniu Result odnajduje Action, przez Action odnajduje Model, aktualizuje Model i tworzy record w `Case.versions`.

To jest **zachowanie/lifecycle trigger**, nie bezpośrednia relacja referencyjna w aktualnym modelu danych. Dlatego bezpośrednie `Result → ModelVersion` nie zostaje dodane do katalogu R2.2-A. Jego semantyka należy do R2.6 Lifecycle & ModelVersion.
