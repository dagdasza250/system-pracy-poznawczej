# SPP v0.5.1 — R2.2-B Cardinality & Integrity Contract

**Etap:** `R2.2-B`  
**Wersja:** `0.1-draft`  
**Status:** `DRAFT_FOR_REVIEW`  
**Input:** frozen R2.2-A Relation Inventory  
**Baseline modified:** `NO`

## 1. Cel

Ustalić kardynalności, właściciela referencji i minimalne reguły integralności dla 27 relacji zamrożonych w R2.2-A. Dokument nie zmienia JSON Schema ani aplikacji.

## 2. Reguły globalne

1. **Required field ≠ non-empty collection.** JSON Schema może wymagać pola-tablicy bez `minItems`; dlatego minimum `1..N` jest przyjmowane tylko wtedy, gdy wspierają je zamrożona semantyka i/lub ścieżka aplikacji.
2. **Case-local integrity.** Fragment, Unit, Relation, Hypothesis, Model, Action, Result i ModelVersion-record nie mogą być referencjonowane między różnymi Case.
3. **Source-layer integrity.** Episode wskazuje dokładnie jeden istniejący Source; Segment wskazywany przez Episode/Fragment musi pochodzić z właściwego Source/Episode.
4. **No silent orphaning.** Fizyczne usunięcie obiektu będącego celem aktywnej referencji jest w fazie eksperymentalnej zabronione. Semantyka archive/supersede należy do R2.6.
5. **No duplicate IDs in one reference list.** Listy `...Ids[]`, support/challenge itp. nie mogą zawierać tego samego ID wielokrotnie.
6. **Schema enforcement is partial.** Obecny JSON Schema najczęściej sprawdza typ/string, ale nie istnienie targetu ani zgodność między polami.
7. **Action↔Result source of truth.** `Result.actionId` jest kanoniczną referencją właścicielską; `Action.resultIds[]` jest odwrotnym indeksem i musi być z nią zgodny.
8. **R2.5 boundary.** Tam, gdzie minimum zależy od provenance (np. Unit→Fragment, Hypothesis→support), R2.2 przyjmuje strukturalne `0..N`, a regułę semantycznego minimum pozostawia R2.5.

## 4. Najważniejsze decyzje R2.2-B draft

### 4.1 Episode
- `Episode.sourceId = exactly 1 Source`.
- `Episode.segmentIds = 1..N Segment`.
- każdy Segment Episode musi należeć do wskazanego Source.
- ten sam Segment może być użyty przez wiele Episode.

### 4.2 Case
- Case ma `1..N Source` oraz `1..N Episode` w eksperymentalnej ontologii.
- każdy `Episode.sourceId` używany przez Case musi występować w `Case.sourceIds`.
- obiekty analityczne przechowywane w Case mają dokładnie jednego właściciela Case.

### 4.3 Fragment / Unit
- Fragment wskazuje dokładnie jeden Episode i `1..N` Segment tego Episode.
- `Unit.fragmentIds` pozostaje strukturalnie `0..N`; R2.5 zdecyduje, dla których typów Unit minimum wynosi co najmniej 1.

### 4.4 Relation
- oba endpointy wskazują dokładnie po jednym Unit w tej samej Case.
- self-loop jest jeszcze decyzją Review B02.
- dłuższe cykle grafu nie są automatycznie błędem.
- identyczny triple `(from,type,to)` nie może występować dwa razy w tej samej Case.

### 4.5 Hypothesis / Model
- support/challenge i modelowe listy referencyjne mogą być puste na poziomie R2.2.
- ich semantyczne minima i wymagania dowodowe należą do R2.5.
- wszystkie targety muszą istnieć w tej samej Case.

### 4.6 Action / Result
- Action wskazuje dokładnie jeden Model.
- Result wskazuje dokładnie jeden Action.
- Action może mieć `0..N` Result.
- proponowane rozstrzygnięcie B04: `Result.actionId` = source of truth; `Action.resultIds[]` = reverse index.

### 4.7 ModelVersion-record
- rozpoznany ModelVersion-record wskazuje dokładnie jeden Model poprzez `entityType=model + entityId`.
- Model może mieć `0..N` rekordów wersji na poziomie R2.2; wymóg tworzenia pierwszej wersji i lifecycle należy do R2.6.
- schema nadal nie typuje `case.versions[]`, więc jest to `SCHEMA_GAP`.

## 5. Otwarte do Review

- `B01` — czy `Case.sourceIds` ma być dokładnie zbiorem źródeł użytych przez `Case.episodeIds`, czy dopuszczalnym nadzbiorem;
- `B02` — czy self-loop dla Relation ma być zawsze zabroniony, czy zależny od typu relacji;
- `B03` — zakres unikalności ID: globalny czy case-local dla obiektów analitycznych;
- `B04` — potwierdzić `Result.actionId` jako source of truth i `Action.resultIds[]` jako reverse index.

## 6. Gate docelowy R2.2-B

Przed `READY_FOR_SIGNOFF` każda z 27 relacji musi mieć jednoznaczne:
- allowed;
- required / structural minimum;
- min/max;
- reference owner;
- referential integrity;
- orphan rule;
- sharing rule;
- cycle/self-loop rule, gdzie dotyczy;
- delete/archive boundary;
- schema enforcement status;
- zgodność z seedem i ścieżką aplikacji.
