**Etap:** R2.2  
**Podetap:** R2.2-A — Relation Inventory  
**Status:** DRAFT_FOR_REVIEW

**Baseline modified:** `NO`

## 0. Cel

Ten dokument nie ustala jeszcze kardynalności. Jego celem jest wyłącznie odpowiedź:

> Jakie relacje rzeczywiście istnieją w v0.5.1, gdzie są zapisane i jaki jest ich obecny stopień formalizacji?

Relacje są rozdzielone na cztery klasy:

- `STRUCTURAL_CONTAINMENT` — obiekt fizycznie przechowuje inne obiekty;
- `EXPLICIT_REFERENCE` — pole `...Id` / `...Ids` wskazuje inny obiekt;
- `SEMANTIC_EDGE` — osobny obiekt `Relation(from,type,to)`;
- `IMPLEMENTATION_REFERENCE` — referencja sterująca UI, walidacją albo redundantny backlink, która nie jest jeszcze częścią kanonicznego rdzenia ontologii.

Brak kardynalności w tym dokumencie jest zamierzony.

# 2. Relacje potwierdzone przez seed

Seed nie tylko posiada pola — pokazuje ich aktualne użycie.

## 2.1 Source / Episode / Case

Seed zawiera:
- Source `src-70` z Segmentami `seg-1 … seg-13`;
- Episode `ep-3` z `sourceId="src-70"` i listą tych Segmentów;
- Case `case-1` z `sourceIds=["src-70"]` i `episodeIds=["ep-3"]`.

To potwierdza istnienie:
- I01 Source → Segment;
- I02 Episode → Source;
- I03 Episode → Segment;
- I04 Case → Source;
- I05 Case → Episode.

Nie dowodzi jeszcze maksymalnych kardynalności.

## 2.2 Fragment / Unit

Fragmenty w seedzie wskazują `episodeId` i `segmentIds`. Unit wskazują `fragmentIds`.

To potwierdza:
- I14 Fragment → Episode;
- I15 Fragment → Segment;
- I18 Unit → Fragment.

W seedzie każdy istniejący Unit ma co najmniej jeden Fragment, ale to jest fakt o seedzie, nie jeszcze reguła ontologiczna.

## 2.3 Semantic Relation

`case.relations` zawiera dziewięć krawędzi, np.:
- `u-1 --wspiera--> u-2`;
- `u-3 --uzupełnia--> u-2`;
- `u-6 --dotyczy innego poziomu niż--> u-7`;
- `u-10 --ogranicza pewność--> u-6`.

Wszystkie przykłady seedu mają endpointy będące Unit.

**Ważne:** schema nie ogranicza `from` i `to` do Unit. Seed pokazuje praktykę `Unit → Unit`, ale nie wystarcza jeszcze do zamrożenia jej jako jedynej dozwolonej domeny.

## 2.4 Hypothesis → Unit

W seedzie `support[]` i `challenge[]` zawierają ID Unit (`u-*`).

Przykład:
- `h-1.support = [u-5,u-6,u-7]`;
- `h-1.challenge = [u-10]`.

To daje mocny dowód, że aktualna semantyka danych używa:
- I21 Hypothesis → supporting Unit;
- I22 Hypothesis → challenging Unit.

Schema sama tego typu docelowego nie deklaruje.

## 2.5 Model → Hypothesis / Unit

Seed jawnie wykorzystuje:
- `hypothesisIds = [h-*]`;
- `supportUnits = [u-*]`;
- `challengeUnits = [u-*]`.

To potwierdza I23–I25.

## 2.6 Action / Result

Seed ma Action `a-1` z `modelId="m-3"` i pustym `resultIds=[]`.

Nie ma początkowego Result, więc:
- Action → Model jest potwierdzone danymi;
- Action → Result istnieje jako przewidziane pole, ale seed nie zawiera jeszcze instancji tej relacji;
- Result → Action nie ma instancji w seedzie początkowym.

# 3. Relacje wynikające z zachowania aplikacji

Aplikacja dostarcza istotnych danych o tym, jak relacje są tworzone operacyjnie.

## 3.1 Episode jest tworzony z aktywnego Source i wybranych jego Segmentów

`episodeModal()` filtruje zaznaczone ID do Segmentów bieżącego Source i zapisuje:
- `sourceId = s.id`;
- `segmentIds = ids`.

To jest silniejszy dowód operacyjny niż samo schema: aplikacja w normalnej ścieżce nie tworzy Episode z Segmentów innego Source.

## 3.2 Case jest tworzony z Episode

`caseModal()` tworzy:
- `sourceIds=[e.sourceId]`;
- `episodeIds=[e.id]`.

W ścieżce walidacyjnej `prepareSPPValidationCase()` robi to samo dla nowo utworzonego Source/Episode.

To wskazuje zamierzoną spójność `Case.episodeIds → Episode.sourceId ∈ Case.sourceIds`, choć schema jej nie wymusza.

## 3.3 Unit jest tworzony razem z Fragment

`unitModal()`:
1. wybiera Segmenty należące do aktywnego Episode;
2. tworzy Fragment z `episodeId=e.id`, `segmentIds=ids`;
3. tworzy Unit z `fragmentIds=[fid]`.

Normalna ścieżka aplikacji tworzy więc ślad:

`Source/Segment → Episode → Fragment → Unit`.

Nie oznacza to jeszcze, że R2.2 ma ustalić kardynalność `Unit → Fragment` na podstawie samego UI; jest to dowód zachowania baseline.

## 3.4 Hypothesis.support jest operacyjnie Unit[]

`hypothesisModal()` buduje listę wyboru z `c.units` i zapisuje wybrane ID do `support`.

Aplikacja zatem jednoznacznie interpretuje `Hypothesis.support` jako referencje do Unit.

Dla `challenge` obecny modal zapisuje pustą listę; seed zawiera jednak Unit IDs w `challenge`.

## 3.5 Model referencje są wyprowadzane z Hypothesis i Unit

`modelModal()`:
- zapisuje wybrane `Hypothesis.id` w `hypothesisIds`;
- agreguje `hypothesis.support` do `supportUnits`;
- agreguje `hypothesis.challenge` do `challengeUnits`.

To potwierdza typy I23–I25 w zachowaniu aplikacji.

## 3.6 Action / Result / ModelVersion

`actionModal()` tworzy Action z `modelId`.

`resultModal()`:
- tworzy Result z `actionId`;
- dodaje Result.id do `Action.resultIds`;
- pobiera Model przez `Action.modelId`;
- aktualizuje `Model.version`;
- zapisuje rekord w `Case.versions` z `entityType="model"` i `entityId=model.id`.

Operational chain baseline’u jest więc:

`Model ← Action ↔ Result → aktualizacja Model → Version-record(Model)`

Kierunki strzałek w powyższym zapisie oznaczają referencje techniczne, nie jeszcze ustalone kardynalności.

# 4. Relacje obecne tylko poza formalnym rdzeniem schema

## R2.2-I29 — Action → Case przez `action.caseId`

Seed oraz `actionModal()` zapisują `caseId` w Action.

Jednocześnie `$defs/action` w JSON Schema nie definiuje pola `caseId`.

Ponieważ Action jest już zagnieżdżony w `case.actions`, jest to redundantny backlink implementacyjny.

**Klasyfikacja:** `DATA_AND_APP_ONLY / SCHEMA_UNTYPED_FIELD`.

Nie należy automatycznie uznawać go za kanoniczną obowiązkową relację R2.2.

## R2.2-I30 — ModelVersion-record → Model przez `entityId`

Seed i aplikacja zapisują:
- `entityType="model"`;
- `entityId=<Model.id>`.

Schema nie typuje elementów `case.versions`.

**Klasyfikacja:** `DATA_AND_APP_ONLY / SCHEMA_GAP`.

To jest kontynuacja rozstrzygnięcia R2.1 dla ModelVersion.

# 5. Relacje ogólne wymagające szczególnego rozstrzygnięcia

## 5.1 Relation.from / Relation.to

Schema:
- wymaga `from`, `type`, `to`;
- wszystkie trzy pola endpointów są tylko ID/string.

Aplikacja posiada kontrolowany katalog nazw relacji:
- wspiera;
- podważa;
- wynika z;
- interpretuje;
- uzupełnia;
- poprzedza;
- powoduje;
- jest przykładem;
- jest wyjątkiem;
- pozostaje w sprzeczności;
- dotyczy innego poziomu niż;
- ogranicza pewność;
- wymaga sprawdzenia.

Seed wykorzystuje Relation wyłącznie pomiędzy Unit.

R2.2 musi później rozstrzygnąć:
- czy endpointem Relation może być tylko Unit;
- czy również Hypothesis / Model / inne obiekty;
- czy self-loop jest dozwolony;
- czy duplikaty są dozwolone;
- czy kierunek ma znaczenie dla każdego typu;
- które typy są symetryczne/asymetryczne.

## 5.2 Fragment.contextBeforeIds / contextAfterIds

Schema definiuje te pola jako listy stringów bez wskazania typu docelowego.

Seed ma je puste, a aplikacja przy tworzeniu Fragmentu również zapisuje puste listy.

Nie ma wystarczających danych, aby w R2.2-A stwierdzić, czy mają wskazywać:
- Segment;
- Fragment;
- dowolny kontekst;
- inny typ.

**Status:** `UNRESOLVED_TARGET_TYPE`.

# 6. Referencje implementacyjne, których nie należy mieszać z ontologią R2

Baseline zawiera również wskaźniki stanu aplikacji:

- `activeSourceId → Source`;
- `activeEpisodeId → Episode`;
- `activeCaseId → Case`;
- `selectedSegmentIds → Segment[]`;
- `selectedEntity {type,id} → aktualnie zaznaczony obiekt`.

Warstwa Walidacji 02 zawiera m.in.:
- `ValidationSession.materialId → ValidationMaterial`;
- `ValidationSession.caseId → Case | null`.

Są to realne referencje baseline’u, ale nie opisują ontologicznej struktury poznawczej `Source → ModelVersion`.

**Klasyfikacja:** `IMPLEMENTATION_REFERENCE / OUTSIDE_CORE_R2.2_DOMAIN`.

Należy je zachować w raporcie zgodności, ale nie używać do definiowania kardynalności rdzenia ontologii.

# 8. Najważniejsze wnioski z inwentarza

### Wniosek A — baseline posiada relacje dwukierunkowo zapisane tylko w jednym miejscu systemu

Action/Result ma oba kierunki:
- `Action.resultIds`;
- `Result.actionId`.

To rodzi pytanie o źródło prawdy i synchronizację, ale nie rozstrzygamy tego jeszcze.

### Wniosek B — większość referencji nie ma integralności referencyjnej w JSON Schema

`$ref` do `$defs/id` potwierdza tylko, że wartość jest niepustym stringiem. Nie sprawdza, czy wskazany obiekt naprawdę istnieje ani czy jest właściwego typu.

### Wniosek C — containment i semantic provenance to różne rzeczy

`Case.contains(Unit)` nie oznacza tego samego co `Unit.references(Fragment)`.

R2.2 musi osobno traktować:
- własność/containment;
- referencję;
- semantyczną krawędź Relation;
- backlink.

### Wniosek D — istnieją dwa miejsca wymagające rozstrzygnięcia typu celu przed kardynalnościami

1. `Relation.from/to`;
2. `Fragment.contextBeforeIds/contextAfterIds`.

Dla tych pól nie da się uczciwie zamrozić pełnej kardynalności, dopóki nie rozstrzygniemy domeny endpointu.

### Wniosek E — ModelVersion nadal pozostaje schema gap

R2.2 może opisać relację wersjonowania, ale nie może udawać, że schema v0.5.1 posiada formalny typ ModelVersion.

## Następny krok

Nie przypisujemy jeszcze od razu wszystkich `1:N`.

Najpierw należy zrobić **R2.2-A Review Gate** i rozstrzygnąć trzy kwestie przed kardynalnościami:

1. Czy `Relation.from/to` są ograniczone do Unit, czy mają być polimorficzne?
2. Co oznaczają `Fragment.contextBeforeIds/contextAfterIds` i jaki jest ich typ docelowy?
3. Czy `Action.caseId` jest częścią ontologii, czy wyłącznie redundantnym polem implementacyjnym?

Dopiero po tych trzech decyzjach powstaje `R2.2-B — Cardinality & Integrity Contract`.
